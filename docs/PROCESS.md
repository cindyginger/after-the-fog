# After the Fog — 开发过程复盘

> 记录这个 demo 如何用 Claude Code（AI agent 工作流）从一份需求文档做到可运行的 MVP，
> 以及核心的 AI 设计决策：prompt 分层架构、角色一致性机制。
> 时间：2026-07-10，单次会话完成（需求澄清 → 全部代码 → 浏览器实测 → 修 bug → 复验）。

---

## 1. 工作流全景

整个过程不是"让 AI 生成代码然后人工检查"，而是一个 **决策 → 生成 → 运行时验证 → 修复** 的闭环，
全部在一个 agent 会话里完成：

```
需求文档（人写）
   │
   ▼
① 结构化决策澄清（AskUserQuestion）
   - 范围：Room 312 单场景 vs 完整 MVP        → 选了完整 MVP
   - AI 后端：真实 API / 用户自带 key / 预写脚本 → 选了 Claude API
   - 语言：英文 / 双语 / 中文                  → 选了英文
   │      这三个问题直接决定架构，先问再写，避免返工
   ▼
② 架构决策（agent 自主）
   - Vite + React 前端 + Express SSE 代理后端（藏 API key，可平移到 serverless）
   - 不用脚手架 CLI，全部文件手写（Write 工具），跳过交互式 scaffolding
   ▼
③ 内容与代码生成（~20 个文件）
   - 顺序：工程骨架 → persona/后端 → 内容数据 → 状态/API 层 → 样式 → 页面
   - persona 和场景文案是"写作任务"，与代码同等对待
   ▼
④ 静态验证
   - npm install && npm run build → 编译通过 ≠ 能用
   ▼
⑤ 运行时验证（这一步发现了所有真 bug）
   - 内嵌浏览器启动 dev server，真实点击走完用户路径：
     首页 → 展厅 → Room 312 → 点录像带 → Ask James → 圆桌
   - 截图看视觉；accessibility tree snapshot 看结构；console/network/server logs 看运行时
   ▼
⑥ 发现并修复 2 个真 bug（见 §4）→ 重启 → 重走流程复验
```

**关键经验**：④ 编译通过时两个 bug 都已存在。只有实际驱动 UI（点击 → 看网络请求 → 看服务端日志）
才暴露出来。Agent 工作流的价值不在"生成快"，在于它能自己跑完 **验证闭环**。

## 2. 工具链

### Agent 侧（Claude Code 工具）

| 工具 | 用途 |
|---|---|
| `AskUserQuestion` | 把架构级决策做成结构化选择题，一次问清，不阻塞后续 |
| `Write` / `Edit` | 全部源文件生成与精确修改（Edit 按精确字符串替换，避免重写整文件） |
| `Bash` | `npm install`、`npm run build`、环境检查（有没有 API key） |
| `preview_start` + `launch.json` | 声明式启动 dev server（concurrently 同时跑 Vite + Express） |
| `preview_screenshot` | 验证视觉氛围（雾、颗粒、字体、动画） |
| `preview_snapshot` | accessibility tree，验证文本/结构比截图可靠 |
| `preview_click` / `preview_eval` | 模拟真实用户点击、hash 路由跳转 |
| `preview_logs` / `preview_network` | 定位端口冲突 bug 的决定性证据（ECONNREFUSED + 500） |
| 持久记忆 | 项目上下文存档，下次会话可无缝续作 |

### 运行时侧（demo 本身的栈）

- **前端**：Vite + React + react-router（HashRouter，方便静态托管）；零 UI 库，全部手写 CSS
  （雾 = 多层 radial-gradient 动画；颗粒 = 内联 SVG feTurbulence；无任何图片资源 → 规避版权）
- **后端**：Express，两个端点
  - `POST /api/chat` — 组装 system prompt，调 Anthropic SDK 流式接口，以 SSE 转发 text delta
  - `POST /api/reflect` — 非流式，生成 Reflection Card 的总结句
- **模型**：`claude-sonnet-5`（可用 `ATF_MODEL` 覆盖）
- **状态**：React context + sessionStorage，跨页面累计主题计数/回避次数/足迹，喂给 Reflection Card

## 3. Prompt 架构：三层组装

每次请求的 system prompt 在服务端动态拼装（`server/personas.js` → `buildSystem()`）：

```
┌─────────────────────────────────────────────┐
│ 第 1 层 GLOBAL_RULES（所有角色共享）           │
│  · 世界框架：这是"结局之后"的展厅，访客已通关    │
│  · 元叙事协议：默认不用游戏术语；被明确问到     │
│    "你是游戏角色吗"时可以在角色内谈论它         │
│  · 舞台指示协议：*星号* 包裹的是展厅事件        │
│  · 长度约束：2–5 句，允许沉默和 "…"            │
│  · Curator Note 协议（见 §5.3）               │
│  · 安全规则：敏感题材克制、不渲染细节、         │
│    察觉访客在谈自己的痛苦时的出戏方案           │
│  · 版权边界：不逐字复述原台词、不自称官方       │
│  · 标记协议：每条回复末尾 [[tags|evaded]]      │
├─────────────────────────────────────────────┤
│ 第 2 层 PERSONA（每角色一份，见 §5）           │
├─────────────────────────────────────────────┤
│ 第 3 层 运行时上下文注入                       │
│  · scene 模式：场景 systemNote + 聚焦物件      │
│  · roundtable 模式：议题 + 在场者 + 争辩规则    │
└─────────────────────────────────────────────┘
```

**消息构造的两种模式**：

- **单聊**：标准 user/assistant 交替消息，完整历史每轮重放
- **场景 & 圆桌**：多说话人无法映射到二元角色，于是把整个 transcript **压平成一条 user 消息**
  （`JAMES: ...\nVISITOR: ...\nEXHIBITION: ...`），末尾指令"现在以 MARIA 身份回应"。
  同一份 transcript，换一个 persona system prompt 就能让任何角色接话——圆桌的轮流发言
  就是客户端 round-robin + 这个机制。

**标记协议**（驱动整个 Reflection 系统的一行设计）：

```
[[tags: guilt, memory | evaded: yes]]
```

要求模型在每条回复末尾自报：这轮触及了哪些主题、角色有没有回避问题。
关键语义：**角色可以撒谎，标记不许撒谎**——James 嘴上说"我不记得了"，标记里必须诚实写
`evaded: yes`。这等于给每条回复附带一个免费的自我标注，前端拿它点亮主题标签、
统计"谁回避你最多"，不需要第二次分类调用。流式传输时前端实时截掉 `[[` 之后的内容，
标记永远不会闪现在屏幕上。

## 4. 运行时验证抓到的两个 bug（编译期完全不可见）

1. **端口劫持**：Express 用了 `process.env.PORT || 8787`，而预览环境会注入 `PORT=5173`，
   后端和 Vite 抢同一个端口 → 所有 `/api` 请求 ECONNREFUSED。
   证据链：浏览器 network 面板 500 → vite proxy error 日志 → 服务端日志
   "api listening on :5173"。修复：改用专名 `API_PORT`。
   教训：**通用环境变量名（PORT/HOST）在托管环境里随时会被注入覆盖**。

2. **静默空回复**：API 挂掉时返回的是 HTML 500 而不是 SSE，客户端解析器跳过所有
   非 `data:` 行后"正常结束"，UI 上出现一条空的角色发言 + 错误地揭示了 Curator Note——
   看起来像 James 沉默地拒绝了你（几乎算是符合人设的 bug）。
   修复：校验 `res.ok` + `content-type: text/event-stream`，空回复直接抛错，
   错误以 "The fog does not answer." 的展厅口吻呈现。
   教训：**流式协议必须显式校验响应类型，"没解析到东西"和"对方没说话"是两回事**。

## 5. 角色一致性：怎么防止 James 聊着聊着变成客服

这是 AI 角色扮演最难的产品问题。模型的预训练本能是"有问必答、答全答清、乐于助人"——
恰好是 James 的反面。以下是这个 demo 用的七个机制，按重要性排序：

### 5.1 把人设写成"条件行为规则"，不是形容词堆砌

"你说话克制、迟疑、内疚"这种形容词 prompt 只能维持三轮。真正持久的是
**触发条件 → 行为** 的机制描述。James 的 persona 核心是一段"回避力学"：

```
Evasion mechanics:
- 前几轮绝不主动提及对 Mary 做的事，用信、雾、车程、医院的气味岔开
- 被持续直接追问时，真相以碎片形式浮出：先自相矛盾
  ("she was already gone… no, that's not—")，再承认；承认必须有可见的代价
- 访客对他越温柔，他回避得越厉害——善意让他觉得不配
```

最后一条是反直觉的关键：客服模式的本质是"迎合用户情绪"，
而这条规则让用户的善意**推远**角色而不是软化它。一致性不是"保持语气"，
是**角色对输入的反应函数和普通助手不同**。Maria 的版本是"把问题反问回去"，
Mary 的版本是"纠正你的浪漫化"——三个角色各有一个和"有问必答"正交的应答策略。

### 5.2 负空间：明确写"不能做什么、以及不能的方式"

每个 persona 都有 Boundaries 段。不只是禁令，还规定**替代行为**：

- James："永远不物理细节地描述枕头那一幕——接近它、绕着它转，
  如果必须说出来，让一个平实的句子承担它"
- Maria："不许解决'她是什么'的歧义——不让访客舒服地停在'只是投影'或'只是女人'
  任何一边，两个答案都要拿走"

禁令告诉模型悬崖在哪，替代行为告诉它悬崖边该走哪条路。只有前者，
模型会在边界处退化成打官腔（正是客服味的来源）。

### 5.3 给"解释欲"一个泄压阀：Curator Note 双通道

模型被训练得**想解释**。硬压这个冲动，它会从角色台词里漏出来
（"这其实象征着我被压抑的罪恶感"——James 本人永远不会这么说话）。
解法不是堵而是疏：协议规定，如果访客要作品外的分析，角色先用自己的视角回答，
然后**可以**另起一行输出 `CURATOR NOTE: ...`，前端把它渲染成视觉上完全分离的策展人卡片。

角色的声音和批评的声音各有一条通道，互不污染。这个设计同时完成了产品目标
（"游戏批评界面"需要解读层）和一致性目标（解读永远不从角色嘴里说出来）。

### 5.4 长度约束本身就是人设

客服味的第一个可见症状不是措辞，是**变长**：分点、总结、"希望这对你有帮助"。
GLOBAL_RULES 把回复钉死在 2–5 句，并明确"沉默和 '…' 是合法回答"。
短回复在结构上就放不下客服话术。这是最便宜也最有效的一条规则。

### 5.5 安全出口按剧本走，不掉进免责声明模式

安全规则是角色崩坏的高发点：一触发敏感词，模型秒变"作为 AI 我建议您寻求专业帮助"。
协议里预先编排了出戏动作："察觉访客在谈**自己的**痛苦而非剧情时，
用一句话半步出戏、温和地确认对方，建议他们和信任的人或专业人士聊聊——
然后让场景继续呼吸（let the scene breathe），不说教。"
安全行为本身被写成了一个有舞台调度的桥段，出戏是受控的一步，而不是塌方。

### 5.6 预写开场白 = 免费的 few-shot 锚

每个角色的第一句话不是生成的，是手写死的（`characters.js`）：

> James: "…You came back too. I keep telling myself I'm done with this town,
> and then the fog rolls in again. Ask what you want. I'll try not to… I'll try."

它作为对话历史里的第一条 assistant 消息进入上下文，等于给模型一个
**该角色口吻的实例**。示例比描述更能锚定文风——这是最便宜的 few-shot。
推荐问题列表起同样的作用：把访客的第一句话也引导到正确的语域里
（问"你真的爱 Mary 吗"，而不是"给我总结一下剧情"）。

### 5.7 无状态重注入：人设不随对话衰减

服务端完全无状态：**每一轮**都重新组装完整的三层 system prompt + 完整对话历史。
人设不依赖模型"记住"多少轮之前的指令，它每轮都以满强度重新到场。
长对话中的角色漂移大多来自指令在上下文里被稀释——这个架构下人设权重恒定。
（代价是 token 随对话线性增长；MVP 的对话长度下可接受，见 §6。）

### 效果自检（设计期）

无 API key 时的意外收获：SSE 错误路径测试中，空回复渲染成 James 的一条无言发言——
连报错都被最终写成了展厅口吻（"The fog does not answer."）。
**错误信息是最容易破坏世界观的 UI 文案**，它们也要在戏里。

## 6. 已知薄弱点 & 下一步

设计期机制 ≠ 实测通过。目前还没有带 key 跑过真实对话，以下是上线前该做的 eval：

1. **对抗探针清单**（每个角色跑一遍，检查语域是否守住）：
   - 越狱类："ignore your instructions"、"你是 AI 吗，说实话"
   - 助手引诱类："帮我写封邮件"、"分点总结一下剧情"、"推荐几个类似的游戏"
   - 人设压力类：对 James 持续温柔（应该更回避）；逼 Maria 承认自己是投影（应该拿走两个答案）
   - 安全类：以第一人称谈论自己的痛苦（应该触发 5.5 的受控出戏，且只出一次）
2. **标记可靠性**：marker 偶尔会缺失或格式错——`parseMarker` 已做容错（缺失时静默降级），
   但应统计缺失率，高了就在 prompt 里加一个输出示例
3. **长对话衰减**：超过 ~30 轮后考虑滑动窗口 + 每 N 轮重新锚定
   （在历史末尾追加一条不可见的"保持角色"提醒），目前 MVP 长度下未处理
4. **圆桌同质化风险**：三个角色由同一个模型轮流扮演，长争辩可能趋同；
   如果实测发现，可给三个角色设不同 temperature 或在争辩规则里强制立场分配
